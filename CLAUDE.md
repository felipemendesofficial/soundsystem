@AGENTS.md

## What this is

Controle de Estoque + Financeiro — a **multi-tenant** stock/inventory and financial management system. Two major subsystems share the app shell: a **Kardex with moving weighted-average cost** (incoming/outgoing stock movements per product per warehouse) and a **Financeiro module** (contas a pagar/receber, its own moving ledger, bank reconciliation, transfers, card/check handling). Multi-warehouse, multi-company, multi-user, with role-based permissions. Stack: Next.js 16 (App Router) + TypeScript + Prisma 7 + PostgreSQL + Auth.js (NextAuth v5 beta). All UI text, code comments, and domain terms are in Brazilian Portuguese.

## Commands

```bash
npm install                    # install deps
docker compose up -d           # start local Postgres (see docker-compose.yml for port/creds)
npx prisma migrate dev         # apply schema migrations (creates a new one if schema changed)
npx prisma generate            # regenerate Prisma Client into src/generated/prisma (needed after schema.prisma changes, or after a fresh clone/install)
npm run db:seed                # (re)seed test users + a default warehouse — see prisma/seed.ts
npm run dev                    # Next.js dev server with Turbopack, http://localhost:3000
npm run build                  # production build (next build — does NOT run prisma generate itself, run it first if schema.prisma changed)
npm run lint                   # eslint (eslint-config-next core-web-vitals + typescript)
npx tsc --noEmit                # type-check only, without eslint — fast way to verify changes compile
npx prisma studio               # visual DB browser
```

There is no test suite/framework configured in this project (no `test` script, no test files). One-off maintenance scripts live in `prisma/scripts/` (run via `npx tsx prisma/scripts/<nome>.ts`, with `import "dotenv/config"` at the top and `@/lib/db` — not a relative path — for the Prisma import) — e.g. `importar-bancos.ts` (syncs the `Banco` catalog from the live Bacen CSV, idempotent upsert by `ispb`, never auto-run). None of these run automatically; they're deliberately on-demand.

Prisma is configured via `prisma7.config.ts` (Prisma 7's `defineConfig`, not the older `schema.prisma`-only setup), reading `DATABASE_URL` from `.env`. The generated client lives at `src/generated/prisma` (custom `output` in `schema.prisma`), imported as `@/generated/prisma/client` — **not** the default `@prisma/client` path. `src/lib/db.ts` wraps it with `@prisma/adapter-pg` (driver adapter) and a `globalThis` singleton for dev hot-reload.

## Architecture

### Multi-tenancy: Grupo Empresarial / Empresa

The app was retrofitted for multi-tenancy (a pre-existing single-tenant install was migrated live). Hierarchy: **`GrupoEmpresarial`** (top-level tenant, fully isolated from other grupos) → one or more **`Empresa`** → **`Usuario`**. A usuario is fixed to exactly one grupo (`Usuario.grupoId`, nullable **only** for the platform-level `master` perfil) but has access to a *restricted* subset of that grupo's empresas via the `UsuarioEmpresa` join table (not automatic access to every empresa in the grupo). Only Empresa is chosen interactively, at `/selecionar-empresa` right after login (auto-picked if the usuario has exactly one) — Grupo itself is never picked. The active `grupoId`/`empresaId`/`depositoPadraoId` live in the JWT session (`session.user.*`, refreshed via NextAuth's `unstable_update` when switching empresa from `TopBar`'s "Trocar empresa").

- **Grupo-scoped cadastros** (shared across every empresa in that grupo — `grupoId` FK, unique constraints like SKU/nome are `@@unique([grupoId, ...])`): `Produto`, `Categoria`, `UnidadeMedida`, `Fornecedor`, `Cliente`, `Vendedor`, `TabelaPreco`, `Servico`, `PlanoFinanceiro`, `CentroCusto` (and their `Mascara*` definitions).
- **Empresa-scoped, everything operational/transactional** (`empresaId` FK): `Deposito`, `Movimentacao`, `OrdemServico`, `Orcamento`, `Lancamento`, `ContaFinanceira`, `LancamentoFinanceiro`, `Processo`, `Portador`, `ParametroFinanceiro`, `FechamentoDiario`, `TransferenciaEntreContas`, `MovimentoAplicacao`, `OperadoraCartao`. Records nested under one of these (`Baixa`, `Estorno`, `MovimentacaoFinanceira`, `ProdutoEstoque`, line items, etc.) are scoped *transitively* via their parent FK — they don't carry their own `empresaId`/`grupoId`.
- **Genuinely global reference tables** (no `empresaId`/`grupoId` at all, admin-only, under `/admin/*`): `Bandeira`, `Banco`, `AlineaDevolucaoCheque`. Server Actions for these still self-check permission locally (a small `exigirMaster()` helper) since Server Actions bypass layout-level route gating.
- **`master`** is a platform-level `Perfil` value (`Usuario.grupoId = null`) — routed to `/admin` instead of the empresa-picker at login, gated by `podeGerenciarPlataforma` (`src/lib/permissions.ts`) plus confinement in the edge middleware (`src/proxy.ts`, which also blocks non-master from `/admin/*`). Creates Grupos + their first Empresa + first admin Usuario in one transaction (`/admin/grupos/novo`).
- **Critical safety pattern — never resolve tenant from a raw client-supplied FK without checking it belongs to the caller.** A real cross-tenant *write* vulnerability was found this way: `resolverTenantPorDeposito` in `src/lib/kardex.ts` derived `empresaId`/`grupoId` straight from whatever `depositoId` a Server Action received via `FormData`, with nothing checking that depósito actually belongs to the session's empresa (the UI never exposed this since dropdowns only list same-empresa depósitos — but nothing stopped a crafted request). Fixed with `resolverTenantPorDepositoValidado(tx, depositoId, empresaIdEsperada)` — `findFirst({ where: { id, empresaId: empresaIdEsperada } })`, returns `null` (never throws) on a mismatch so the caller can surface a friendly error — used everywhere a `criar*`/`atualizar*` action accepts a user-chosen `depositoId` (the original unchecked resolver stays in use only where the id came from an already-empresa-scoped record, e.g. inside `finalizarOrcamento`/`concluirOrdemServico`). **Apply the identical pattern to any new FK the user picks freely in a form** — e.g. the Cartão Taxa lookup in `lancamentos-financeiros/actions.ts` does `operadoraCartaoTaxa.findFirst({ where: { id, operadora: { empresaId } } })` for the same reason.

### Kardex / moving weighted-average cost engine

The core business logic lives in `src/lib/kardex.ts` and is the most important file to understand before touching stock movements. It exposes four functions — `registrarEntrada`, `registrarSaida`, `registrarTransferencia`, `estornarEntradaNaTransacao` — each wrapping (or expecting) a `db.$transaction`. Key invariants:

- **Row locking via `INSERT ... ON CONFLICT DO UPDATE`**: `obterOuCriarEstoqueTravado` atomically creates-or-locks the `produto_estoque` row for a given (produto, depósito) pair inside the transaction, closing the race-condition window that a plain "check then create" would leave open when two users move the same item concurrently.
- **Entradas** (incoming) recompute the moving weighted-average: `novoCustoMedio = (saldoAtual × custoMedioAtual + qtdEntrada × custoUnitarioEntrada) / novaQuantidade`.
- **Saídas** (outgoing) never change `custoMedioAtual` — they debit at whatever the current average cost is, and throw `SaldoInsuficienteError` if requested quantity exceeds available balance. The one deliberate exception is `estornarEntradaNaTransacao` (used only to reverse a Purchase Budget's — Orçamento de Compra's — closing): it subtracts the exact quantity/value a specific prior entrada added and recomputes the average from what's left, rather than debiting at the current average — see its docstring for why.
- **Transferências** between warehouses are two movements (`transferencia_saida` + `transferencia_entrada`) in one transaction, preserving the source's average cost into the destination. The two `produto_estoque` rows are locked in a deterministic order (`.sort()` on the two depósito IDs) specifically to avoid deadlocks between opposite-direction concurrent transfers.
- Every movement writes an immutable snapshot row to `movimentacoes` (`custoMedioApos`, `saldoQuantidadeApos`, `saldoValorApos`) — this is the actual Kardex ledger, queried by `src/app/(app)/kardex/[produtoId]/page.tsx`. `produto_estoque` is just the current-balance cache per (produto, depósito).
- All quantities/costs are Prisma `Decimal` (`Prisma.Decimal`), never plain JS numbers, inside this module — use `.plus/.minus/.times/.dividedBy/.isZero()` etc., not arithmetic operators.
- A product with `Produto.controlaEstoque = false` can be referenced in movements/OS/Orçamentos, but every kardex function skips the `produto_estoque` mutation for it (balance stays untracked, at zero) while still writing the `movimentacoes` row — see `produtoControlaEstoque` in `kardex.ts`.

When adding a new movement type or changing cost logic, this file's docstring comments explain the *why*; read them before modifying the math.

### Módulo Financeiro

A second major subsystem, built up over many iterative rounds (no single up-front design doc — read the model comments in `schema.prisma` and the docstrings in `src/lib/financeiro-ledger.ts` for the *why* behind anything non-obvious). Hub screen at `/financeiro`; gated by `podeGerenciarFinanceiro` (admin-only, `src/lib/permissions.ts`).

**Core cycle** — mirrors the Kardex's "immutable ledger + balance cache" split: `LancamentoFinanceiro` (a conta a pagar/receber: despesa or receita, with a triple rateio — Plano Financeiro × Centro de Custo nested per line, a parallel Processo tree, plus optional Retenção/Comissão lines) → `Baixa` (settles it against a `ContaFinanceira`, writes an immutable `MovimentacaoFinanceira` row and updates `ContaFinanceira.saldoAtual`, the balance cache) → optionally `Estorno` (reverses one Baixa). A lançamento can accumulate several Baixas over time (one estornada, a new one later) — only one may be *active* (`estornada: false`) at a time, enforced by a partial unique index applied via raw SQL migration, not a Prisma `@@unique` (Prisma 7.10 has no declarative conditional-unique support). All of this lives in `src/lib/financeiro-ledger.ts`.

- **`natureza`**: `prevista` (forecast — can't receive Baixa until `confirmarPrevisao` converts it to `real`) or `real`.
- **Contraparte is mandatory and mutually exclusive**: despesa requires `fornecedorId` (never `clienteId`); receita requires `clienteId` (never `fornecedorId`).
- **`valorBaixado` is always server-computed** (`valorOriginal + juros + multa − desconto − retenções`) — never a value the client submits directly, same "never trust the client for money math" rule as `custoCompraUnitario` in Orçamento.
- **Regras de conta por tipo de documento** (`src/lib/regras-conta-baixa.ts#erroContaParaBaixa`): a fixed compatibility matrix between `ContaFinanceira.tipo` (`conta_corrente`/`caixa`/`fundo_fixo`/`aplicacao`) and `TipoDocumento` (espécie, cheque à vista/prazo/devolvido, depósito-cartório, nota promissória, depósito bancário, pix, cartão) — e.g. despesa can never use an `adiantamentoCliente` account; cartão/pix/depósito-bancário can't go to Caixa; Fundo Fixo never receives receita. Applied both at Baixa time and when picking a lançamento's Conta Prevista — always re-validated server-side, never trust client-side filtering alone.

**Fechamento Diário** (`fecharDia`/`reabrirDia`, same file) closes/reopens days strictly sequentially, no gaps or free choice of date: `calcularProximoDiaAFechar` always returns *(último fechamento ativo + 1 dia)* — or `ParametroFinanceiro.dataInicioControle` if one is configured and nothing has been closed yet (lets a company start the system today but declare "controle começou em 01/09", lançar retroativo, and close forward), or today if neither applies. `validarDataDeMovimento` blocks any lançamento dated outside `(último fechamento, hoje]` (and below `dataInicioControle` before the first fechamento). Re-closing a day that was previously reopened reuses the *same* `FechamentoDiario` row (`upsert`, not `create` — `@@unique([empresaId, data])`; reopening only flips `ativo: false`, it never deletes the row, so a plain `create` on re-close hits the constraint).
  - **Date-handling gotcha, easy to silently reintroduce**: every business date here (`dataBaixa`, `dataEstorno`, Transferência/Aplicação `data`, `dataInicioControle`) comes from an `<input type="date">` — a bare `"YYYY-MM-DD"` string, which `z.coerce.date()` always parses as **UTC midnight** (an ECMA-262 rule for date-only ISO strings). Production runs `TZ=America/Sao_Paulo` (UTC-3, set in `docker-stack.soundsystem.yml`). The internal `inicioDoDia()` helper **must** extract the calendar day using UTC getters (`Date.UTC(data.getUTCFullYear(), data.getUTCMonth(), data.getUTCDate())`) — using local getters/`setHours(0,0,0,0)` here silently shifts every submitted date back one calendar day, which broke Fechamento Diário's "is today already closed" check for as long as the feature existed, undetected. `hoje` ("today", for future-date checks) is the one date that *does* need local getters first — it's a live instant, not a parsed string — so it goes through a **separate**, exported `hojeUTC()` helper (floors the live `new Date()` to the local calendar day, then re-anchors to UTC midnight so it's comparable with everything else). Never collapse these two helpers into one.

**Transferência entre Contas** (`registrarTransferenciaNaTransacao`): 6 tipos (`transferencia_geral`, `reposicao_fundo_fixo`, `saldo_caixa_banco`, `emprestimo_contraido_banco`, `transferencia_entre_caixas`, `transferencia_banco_para_caixa`), each with its own allowed origem/destino `ContaFinanceira.tipo` pair and whether a terceiro (cliente/fornecedor de adiantamento) is allowed on each side — full matrix in `src/lib/regras-conta-transferencia.ts#REGRAS_TRANSFERENCIA`. `emprestimo_contraido_banco` has no real origem (it's new money) — modeled with the sentinel `contaOrigemId === contaDestinoId` — and affects fluxo de caixa via `ParametroFinanceiro.planoEmprestimoId`; it does **not** generate future parcela lançamentos (a schema comment flags this explicitly as out of scope). `SaldoAdiantamentoTerceiro` (a running balance per conta+cliente/fornecedor) is credited *only* by Transferência and debited *only* by Baixa; it has no dedicated ledger table — `src/lib/extrato-adiantamento.ts#obterExtratoAdiantamento` reconstructs its line-by-line history by replaying Baixa/Estorno/Transferência records in memory on every read.

**Cheque de Terceiro**: a Baixa on a `cheque_vista`/`cheque_prazo` receita, once itself baixada into a Caixa account, can be selected — possibly several at once, sum-capped at the despesa's `valorBaixado` — to pay a despesa's Baixa. The vínculo happens *inside* the Baixa form/transaction (`baixa-form.tsx` + `darBaixaLancamento`), not a separate screen. Estornar the despesa's Baixa releases the cheques back in the same transaction; estornar a cheque currently in use is blocked. This is pure traceability, not a second money movement — the cash effect is just two ordinary Baixas (the cheque's own receita, and the despesa it later pays).

**Cartão**: 3-tier cadastro — `Bandeira` (global catalog, `/admin/bandeiras`) → `OperadoraCartao` (per-empresa institutional data, `/operadoras-cartao`) → `OperadoraCartaoTaxa` (Operadora × Bandeira × Modalidade, `@@unique`, holds 4 percentuais — à vista / antecipação / parcelado-estabelecimento / parcelado-cliente — plus prazo de repasse). A cartão `LancamentoFinanceiro` snapshots the chosen percentual into `DadosCartao.percentualAplicado` at creation time (never recalculated later even if the Taxa row changes) — `DadosCartao.tipoTaxa` picks which of the 4 percentuais applied.

**Banco**: global catalog (`Banco`, ~474 rows) backing `ContaFinanceira.bancoId`, sourced from the real Bacen participant list, not hand-typed data. `prisma/scripts/importar-bancos.ts` fetches the live CSV and upserts by `ispb` (the one field every institution is guaranteed to have — `codigoCompe` is optional, some fintechs/IPs don't have one) — safe to re-run any time, but never auto-run in the deploy pipeline (an intentionally manual/on-demand script, unlike `prisma migrate deploy`).

**Conciliação Bancária** (`src/lib/conciliacao.ts`) is still fully manual — no OFX/CSV import, no automatic value/date matching. `Saldo do banco = saldo do sistema − pendências da empresa (assinado) + pendências do banco (assinado)` — two *different* kinds of pendência (`MovimentacaoFinanceira.statusConciliacao = pendente` vs. a separate `PendenciaConciliacao` row) that pull the reconciled balance in opposite directions; get the signs right if touching `obterResumoConciliacao`.

**Comissão de Vendedor**: `Vendedor.saldoComissao` + `MovimentacaoComissaoVendedor` — its own dedicated ledger (unlike `SaldoAdiantamentoTerceiro`) — credited on a receita's Baixa, debited on a despesa's Baixa, both referencing the same `Comissao` rateio line already on the Lançamento.

**Recolhimento de Retenção** groups `pendente` retenções from already-`baixado` lançamentos sharing a `planoId` into one new despesa, created directly via Prisma (bypasses `criarLancamentoFinanceiro`'s generic validation) — so it has no fornecedor. Editing that despesa afterward through the normal screen will then demand one (known rough edge, unresolved).

### Prisma `Decimal` → display formatting gotcha

Aggregate/query results for `Decimal` columns (`quantidadeSaldo`, `custoMedioAtual`, `valorTotalSaldo`, etc.) come back as `Prisma.Decimal` instances, not numbers. Calling `.toLocaleString(...)` directly on one does **not** produce a locale/currency-formatted string — it silently returns the Decimal's own plain string form (e.g. `"25882.56"` instead of `"R$ 25.882,56"`), with no error. Always convert with `Number(valorDecimal)` before calling `.toLocaleString("pt-BR", { style: "currency", currency: "BRL" })`. See the `formatarMoeda`/`formatarNumero` helpers duplicated in a couple of pages (e.g. `src/app/(app)/estoque/page.tsx`) for the working pattern.

### Auth & authorization

- **Auth.js v5 (beta)** with a `Credentials` provider (email + bcrypt-hashed password against `usuarios.senha_hash`) and JWT sessions. `src/lib/auth.config.ts` holds the provider-agnostic config (no Prisma/bcrypt imports) so it's safe to load in the **Edge Runtime**; `src/lib/auth.ts` adds the actual `Credentials` provider on top for use in server components/actions (Node runtime), plus `grupoId`/`empresaId`/`depositoPadraoId` on the session (refreshed via NextAuth's still-`unstable_update` method when the usuario switches empresa). `src/proxy.ts` is the middleware — builds its own lightweight `NextAuth(authConfig)` instance, entirely at the edge: redirects unauthenticated requests to `/login`, confines `master` to `/admin/*` and blocks everyone else from it, forces a non-master usuario with no `empresaId` yet to `/selecionar-empresa`, and gates `/usuarios` to `admin`.
- `trustHost: true` in `auth.config.ts` is required because the app sits behind Traefik in production (see `docker-stack.soundsystem.yml`) — Traefik is the only ingress, so trusting the forwarded Host header is safe there but is a deliberate, documented exception.
- Role-based checks (not middleware-level, just plain functions) live in `src/lib/permissions.ts`, called directly by pages/components (e.g. to conditionally render cost columns) rather than relying solely on the middleware: `podeVerCusto` (admin/estoquista see cost & value figures — the `vendedor` profile never sees margin), `podeGerenciarUsuarios` (admin-only), `podeLancarMovimentacao`, `podeGerenciarOrcamento`, `podeGerenciarTabelaPreco`, `podeGerenciarVendedor`, `podeGerenciarFinanceiro` (admin-only, gates the whole Financeiro module), `podeGerenciarPlataforma` (`master`-only, gates `/admin/*`).

### Route structure (App Router)

- `src/app/(app)/` — the authenticated app shell. `layout.tsx` does a server-side `auth()` redirect-if-unauthenticated, then wraps children in `TopBar` + `BottomNav` (`src/components/app-shell/`) inside a fixed `max-w-[400px]` mobile-first column — this is a phone-oriented UI, not a responsive desktop dashboard.
  - `produtos/`, `fornecedores/`, `clientes/`, `depositos/`, `usuarios/` — CRUD screens for master data, each with `page.tsx` (list) + `actions.ts` (server actions, zod-validated) + a `*-form.tsx` client form shared between "novo" and "editar" (same form component, different `action` passed in and optional `defaultValues`).
  - `movimentacoes/nova/` — the stock-movement entry form; calls into `src/lib/kardex.ts` via its `actions.ts`.
  - `lancamentos/` — a multi-line stock transaction (`Lancamento` → `ItemLancamento`, `tipo`: compra/venda/devolução (cliente/fornecedor)/ajuste (entrada/saída)/perda-avaria/uso-interno/transferência), status `aberto → fechado`/`cancelado`; only `finalizarLancamento` moves stock (one Kardex movement per item), `cancelarFechamentoLancamento` reverses it — same "freeze on close, reverse via the exact-entrada estorno, not a generic saída" shape as Orçamento below. Only `tipo: venda` carries desconto/acréscimo (`modoAjuste`/`formatoAjuste`/`valorAjuste`, same enums and reason to exist as Ordem de Serviço's discount — see below).
  - `estoque/` — current stock position (balances per produto × depósito), filterable by depósito via a URL search param (`?depositoId=`), driven by a small client component (`src/components/deposito-filter.tsx`) that just pushes router state — no client-side data fetching.
  - `kardex/[produtoId]/` — full movement history (the ledger) for one product.
  - `ordens-servico/` — a service order: lines of `produto`/`serviço` for invoicing; only its `concluirOrdemServico` action moves stock (a `registrarSaida` per produto line, `tipoMovimento: "os_saida"`), status `aberta → em_andamento → concluida`/`cancelada`. Discount/acréscimo (`modoAjuste`/`formatoAjuste`/`valorAjuste`) is persisted alongside the item's original price (`precoOriginal`) so reopening to edit never composes a discount on top of an already-discounted price — same pattern (and same enums) reused by `Lancamento`'s `tipo: venda`, above.
  - `orcamentos/` — a purchase budget (rateio de compra): the user enters each item's estimated resale value plus either a resale-rate % or a target total purchase amount; `src/lib/orcamento.ts#calcularRateio` splits that purchase total across items proportional to their estimated value. `finalizarOrcamento` (status `aberto → fechado`) freezes each item's computed `custoCompraUnitario` and calls `registrarEntrada` (`tipoMovimento: "compra"`) per item; `cancelarFechamentoOrcamento` (`fechado → aberto`) reverses those exact entradas via `estornarEntradaNaTransacao`, not a generic saída — see the Kardex section above.
  - `tabela-precos/` — named price lists (`TabelaPreco` → `ItemTabelaPreco`, one price per produto; products only, not serviços). No workflow/status — a plain mutable catalog, like `Servico.precoPadrao`. One tabela per grupo can be flagged `principal` (app-enforced single-flag, not a DB `@unique`) — used as the 2nd tier of the Home's stock valuation fallback (última venda → tabela principal → custo). `Cliente.tabelaPrecoPadraoId` (optional) is the per-client default; picking that cliente in `movimentacao-form.tsx`/`os-form.tsx` pre-selects their tabela client-side and, when a produto is then chosen, suggests its `precoVenda`/`precoUnitario` from that tabela — falling back to the product's last recorded sale price (`src/lib/tabela-preco.ts#obterUltimosPrecosVenda`, a `DISTINCT ON` over `movimentacoes` where `tipo_movimento IN ('venda','os_saida')`) when the tabela has no price for it. Always just a prefill — the field stays editable.
  - `financeiro/` — hub page linking into the Financeiro module below.
  - `contas-financeiras/` — `ContaFinanceira` cadastro (tipo conta_corrente/caixa/fundo_fixo/aplicacao, `bancoId`); `[id]/extrato` (ledger for the conta itself, filterable by período), `[id]/conciliacao` (lançar/vincular/resolver pendências).
  - `lancamentos-financeiros/` — the core screen: `novo`/`[id]/editar` (the triple-rateio form), `[id]` (detail, shows both sides of any Cheque de Terceiro vínculo), `[id]/baixa` (settle, including the Cheque de Terceiro picker when applicable), `[id]/estorno`.
  - `fechamento-diario/` — fechar/reabrir days sequentially; see the Fechamento Diário subsection above before touching this.
  - `transferencias-entre-contas/`, `aplicacoes-financeiras/` — see the respective subsections above.
  - `planos-financeiros/`, `centros-custo/`, `processos/` — hierarchical, máscara-driven cadastros (código always system-assembled from zero-padded segments per level, never free-typed); `src/lib/mascara.ts` + `src/components/arvore-hierarquica.tsx`/`mascara-form.tsx`/`mascara-picker.tsx` are the shared building blocks, reused across all three.
  - `portadores/`, `operadoras-cartao/` (institutional cadastro + `[id]/taxas/*` sub-screens for the Taxa grid), `parametros-financeiros/` (per-empresa singleton config — planos padrão pra Aplicação/Resgate/Rendimento/Empréstimo, multa padrão, `dataInicioControle`), `recolhimentos-retencao/` — smaller cadastro/utility screens for the module.
  - `vendedores/[id]/extrato`, `clientes/[id]/adiantamento`, `fornecedores/[id]/adiantamento` — read-only extrato screens (Comissão / Adiantamento de terceiro) reached from the respective listing, not from the cadastro's edit screen — actions that aren't "editar cadastro" live in the listing, not the edit form.
  - `src/app/admin/` — separate shell, `master`-only (gated by `podeGerenciarPlataforma` at `admin/layout.tsx`, individual actions self-check too since Server Actions bypass layout gating): `grupos/` (create Grupo+Empresa+first admin Usuario), `bandeiras/`, `alineas-devolucao-cheque/` — the genuinely global reference tables.
- List screens that need live text search (`produtos`, `estoque`) use a pattern of: server component fetches everything and maps Prisma rows into a small plain-data shape (formatting `Decimal`s to strings, joining fields), passed as props into a `"use client"` list component (`src/components/produtos-lista.tsx`, `src/components/estoque-lista.tsx`) that holds the search string in local state and filters client-side — no server round-trip per keystroke. Follow this pattern for new searchable lists rather than adding a new fetch-on-type mechanism.
- Server actions follow a consistent shape: a zod `schema`, a `toData`/`lerFormData` helper calling `schema.safeParse`, and exported `criarX`/`atualizarX` functions returning `{ erro?: string }` for `useActionState`, calling `revalidatePath` + `redirect` on success. A prop crossing a Server→Client component boundary must always be a plain serializable value — passing a function (e.g. `hrefItem={(id) => ...}`) throws "Functions cannot be passed directly to Client Components" at runtime, not caught by `tsc`/lint; pass path-prefix strings instead and let the client component concatenate.

### UI components

- `src/components/ui/` is a shadcn-style wrapper layer around **`@base-ui/react`** primitives (not Radix) — e.g. `select.tsx` wraps `@base-ui/react/select`, `combobox.tsx` wraps `@base-ui/react/combobox`. When adding a new primitive-backed component, check `node_modules/@base-ui/react/<name>` for the available parts/props before assuming Radix-style APIs; base-ui's `Select` has no built-in text filtering (use `Combobox` instead when a searchable dropdown is needed — it filters by substring against `itemToStringLabel` by default).
- `components.json` configures `shadcn` CLI generation (`style: "base-nova"`, base color `neutral`, icons via `lucide-react`, path aliases matching `tsconfig.json`'s `@/*`).
- Design tokens (colors, radii) are CSS custom properties in `src/app/globals.css`, mapped into Tailwind v4 via `@theme inline`. Brand-specific tokens (`--brand-yellow`, `--brand-green`, `--shell`, `--text-faint`) sit alongside the standard shadcn palette (`--primary`, `--card`, `--muted`, etc.) — prefer the semantic tokens (`primary`, `accent`, `muted-foreground`...) over hardcoding hex values or introducing new ad-hoc colors.

## Deployment

Production runs as a **Docker Swarm** stack (`docker-stack.soundsystem.yml`) behind Traefik with Let's Encrypt, at `soundsystem.felipemendesoficial.cloud`. There is no CI/CD — deploys are manual: `git pull` on the swarm manager, `docker build -t soundsystem_app:latest .`, then `docker service update --force soundsystem_app` (required because the image tag is `:latest` and Swarm won't pick up a rebuilt image under the same tag otherwise). Local dev's `docker-compose.yml` is separate and unrelated to the production stack file.

The container's `CMD` runs `npx prisma migrate deploy` before `npm run start` — pending migrations apply automatically on every deploy/restart, no separate manual step. `prisma migrate deploy` is idempotent (no-ops when the schema is already current) and takes its own advisory lock, so this is safe even if the service is ever scaled beyond one replica. Don't move this logic out of the image without putting an equivalent step back in the deploy flow — a schema/code mismatch here previously took the app down in production (queries against columns/tables that didn't exist yet) until it was applied manually.

**Genuinely destructive migration (e.g. `DROP COLUMN` on a column with live non-null data)**: `prisma migrate dev --create-only` still triggers Prisma's interactive data-loss confirmation against the connected dev DB and fails outright non-interactively ("environment is non-interactive") *without even creating the migration folder*. The reliable workaround: create the migration folder by hand (`mkdir prisma/migrations/<timestamp>_<nome>`), write the raw SQL into `migration.sql` yourself, then apply with `npx prisma migrate deploy` (which only applies pending files in order, never diffs or prompts). Used for the staged rename pattern seen a few times in this repo — add the new column additively first (safe via a normal `migrate dev`), backfill it at the app level, then drop the old column in a *separate* migration using this manual technique (e.g. `ContaFinanceira.banco` → `bancoId`, `DadosCartao.operadora` → `operadoraId`).
